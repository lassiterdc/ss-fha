# SE Audit — ss-fha Refactor
## 2026-03-14

**Executive Summary**

The most consequential finding is an unseeded RNG in `core/event_statistics.py`: `bs_samp_of_univar_event_return_period` and `bs_samp_of_multivar_event_return_period` call `np.random.choice` with no seed, making event-statistic bootstrap results non-reproducible across runs and non-restartable under Snakemake. This is in direct contrast to `core/bootstrapping.py`, which correctly uses `np.random.default_rng(base_seed + sample_id)`. Second, the `combine_and_quantile` function in `analysis/uncertainty.py` uses `join="outer"` when opening bootstrap sample zarrs, which will silently introduce NaN values if any sample has a different `return_pd_yrs` length -- then the downstream NA check will fail with an opaque error rather than diagnosing the root cause. Third, the `SSFHAConfig` type alias is defined three different ways across three files (`config/model.py`, `validation.py`, `paths.py`), creating a maintenance hazard that will only worsen as new modules import it.

### Section 1: Quick Wins

**1. Replace `assert` with a proper raise in `event_comparison.py`**

`analysis/event_comparison.py` line 435 uses `assert ev_vars is not None` for a runtime validation check. Python's `-O` flag strips `assert` statements entirely, so this guard would silently vanish in optimized execution -- exactly the scenario where a SLURM job might run with `-O` for performance.

- Recommendation: Replace with `if ev_vars is None: raise ConfigurationError(...)`. The comment already acknowledges this is a validated-above guard, but assert is not the right mechanism for runtime checks in production code.
- Effort: `quick-win`

**2. Unseeded RNG in event statistics bootstrap functions**

`core/event_statistics.py` functions `bs_samp_of_univar_event_return_period` and `bs_samp_of_multivar_event_return_period` call `np.random.choice(...)` using the global NumPy RNG with no seed. This means event-statistic bootstrap results are non-reproducible between runs and non-deterministic under parallel Snakemake execution. `core/bootstrapping.py` correctly uses `np.random.default_rng(base_seed + sample_id)`.

- Recommendation: Add a `rng: np.random.Generator` parameter to both functions (no default). Thread a seeded generator from the caller in `analysis/event_comparison.py`. This mirrors the pattern already established in `core/bootstrapping.py`.
- Effort: `quick-win`

**3. Consolidate `SSFHAConfig` type alias to a single canonical definition**

`SSFHAConfig` is defined in three places with three different syntaxes: `Annotated[SsfhaConfig | BdsConfig, Field(discriminator="fha_approach")]` in `config/model.py` line 342, `Union[SsfhaConfig, BdsConfig]` in `validation.py` line 30, and `SsfhaConfig | BdsConfig` in `paths.py` line 48 (inside `TYPE_CHECKING`). Only the `model.py` version carries the discriminator metadata. The other two are plain unions that happen to have the same name.

- Recommendation: Delete the alias definitions in `validation.py` and `paths.py`. Import `SSFHAConfig` from `config.model` everywhere, or use `SsfhaConfig | BdsConfig` directly in type annotations (since neither `validation.py` nor `paths.py` needs the discriminator for Pydantic parsing). The key point is: one definition, one import path.
- Effort: `quick-win`

**4. Delete dead placeholder files `utils.py` and `cli.py`**

`src/ss_fha/utils.py` contains only a `do_something_useful()` function that prints a placeholder message. `src/ss_fha/cli.py` is a Typer skeleton that calls this function. Neither is imported by any production code or test. Per `CONTRIBUTING.md` ("No cruft"), these should be removed. The real CLI is planned for 04B and will replace `cli.py` entirely.

- Recommendation: Delete both files and remove `cli` from any `__init__.py` exports. When 04B lands, `cli.py` will be rewritten from scratch per the plan.
- Effort: `quick-win`

**5. Duplicated `_supported_geo_ext` set between `gis_io.py` and `validation.py`**

`validation.py` line 215 defines `_supported_geo_ext = {".shp", ".geojson", ".json", ".gpkg"}`, duplicating the canonical `_SUPPORTED_GEO_EXTENSIONS` in `io/gis_io.py` line 38. If a format is added to one and not the other, validation will accept files that the loader rejects (or vice versa).

- Recommendation: Import from `gis_io` in `validation.py`: `from ss_fha.io.gis_io import _SUPPORTED_GEO_EXTENSIONS`. Alternatively, promote the set to `constants.py` and import from there in both modules.
- Effort: `quick-win`

### Section 2: Design and Architecture

**1. `join="outer"` in `combine_and_quantile` masks a data integrity bug**

`analysis/uncertainty.py` line 327 uses `join="outer"` when calling `xr.open_mfdataset` to combine bootstrap sample zarrs. The comment says "samples may have different return_pd_yrs lengths; outer preserves all." This is dangerous: if samples genuinely have different `return_pd_yrs` lengths (which happens when bootstrap resampling draws different numbers of events), the outer join fills missing positions with NaN. The downstream NA check on line 346 then raises a `DataError`, but the error message says "investigate before proceeding" -- it does not identify the root cause as mismatched return period axes.

The correct behavior depends on scientific intent. If samples with fewer events should still be included (shorter return period axes), then the quantile computation needs to handle the ragged dimension explicitly (e.g., interpolate to a common return period grid). If all samples should have the same axis length, then `join="exact"` would catch the problem immediately with a clear error.

- Recommendation: Change to `join="exact"` for now, and add a clear error message explaining that mismatched `return_pd_yrs` lengths indicate varying event counts across bootstrap samples. If ragged axes are scientifically intended, implement explicit interpolation to a common grid in a follow-up.
- Effort: `medium`

**2. `ASSIGN_DUP_VALS_MAX_RETURN` is a module-level constant that should be a config field**

`constants.py` defines `ASSIGN_DUP_VALS_MAX_RETURN: bool = False`, which controls empirical CDF behavior for duplicate values in `core/event_statistics.py`. The docstring and the comment both say "Promote to SsfhaConfig when resolved." This constant changes the numerical output of every return period calculation. Leaving it as a hardcoded constant means: (a) it cannot be varied per case study, (b) it is invisible in saved config YAML files, undermining reproducibility, and (c) it will require a code change rather than a config change to test the alternative behavior.

- Recommendation: Add `assign_dup_vals_max_return: bool` to `SsfhaConfig` now, even if the default is `False`. Thread it through `compute_univariate_event_return_periods` and `compute_all_multivariate_return_period_combinations`. This makes the choice visible in the config YAML and reproducible.
- Effort: `medium`

**3. Incomplete validation of physically impossible inputs** *(Lens 4)*

The Pydantic validators and `validation.py` check toggle dependencies and file existence thoroughly, but they do not reject physically or statistically impossible numerical inputs. Specific gaps:
- `alpha` and `beta` (plotting position parameters) on `SsfhaConfig` accept any float, including negative values. The Hazen/Weibull formula `(i - alpha) / (n + 1 - alpha - beta)` produces nonsensical results for alpha or beta outside [0, 1].
- `return_periods` accepts negative integers (e.g., `[-5]` would pass Pydantic but is meaningless).
- `n_years_synthesized` is checked for `<= 0` in `validation.py` but not in the Pydantic model itself, so a config constructed via `load_config_from_dict` bypasses the check if `preflight_validate` is not called.
- `bootstrap_quantiles` on `UncertaintyConfig` has no validation that values are in (0, 1).

- Recommendation: Add `@field_validator` decorators or `model_validator` checks to the Pydantic models for: `alpha in [0, 1]`, `beta in [0, 1]`, `alpha + beta <= 1`, all `return_periods > 0`, `n_years_synthesized > 0`, and all `bootstrap_quantiles` in `(0, 1)`. Pydantic is the right layer for these checks because they are structural constraints, not runtime-discoverable ones.
- Effort: `medium`

**4. `conftest.py` sys.path manipulation in old-code alignment tests is fragile** *(Lens 9)*

`tests/test_old_code_alignment/conftest.py` inserts `_old_code_to_refactor/` into `sys.path` at module level and injects mock modules into `sys.modules`. This runs at pytest collection time for every test session, even when old-code alignment tests are not selected. The `sys.path` insertion is guarded by `if _old_code_dir not in sys.path`, but `sys.modules` entries are unconditionally overwritten. If any future production code or test inadvertently imports a module named `local` or `__inputs`, the mock will shadow it silently.

- Recommendation: Move the `sys.modules` manipulation into a session-scoped fixture with `autouse=True` that is only active within the `test_old_code_alignment` package. Alternatively, use a `conftest.py` plugin that registers these mocks only when the test collection includes that directory. The `sys.path.insert` should use `pytest`'s `monkeypatch` rather than direct mutation to ensure cleanup.
- Effort: `medium`

**5. No documented dimension/coordinate convention** *(Lens 5)*

Dimension naming is consistent across implemented modules (event_iloc, x, y, return_pd_yrs, quantile), but there is no single reference document or code artifact that defines the convention. Each module's docstring describes its own dimensions but does not reference a shared contract. When Phase 3D (PPCCT) and 3E (comparison) add new dimension names (e.g., bootstrap_sample, comparison_pair), the lack of a central registry will make it easy to introduce inconsistencies.

- Recommendation: Add a `DIMENSION_NAMES` section to `constants.py` (or a new `conventions.py`) that documents the canonical dimension names as string constants, with comments explaining each. Import these constants in modules that create or validate dimensions. This is a lightweight contract that prevents drift without adding enforcement overhead.
- Effort: `medium`

- `config/loader.py`: `_deep_merge` and `_fill_placeholders` have no unit tests. Template placeholder edge cases (nested placeholders, empty strings) are untested.

- `validation.py`: No tests for `validate_config`, `validate_input_files`, or `validate_workflow_inputs`. The preflight validation layer is entirely untested.

**`full_config` fixture will fail at Pydantic validation**

`tests/conftest.py` lines 110-113 define the `uncertainty` section as `{"n_bootstrap_samples": 10, "bootstrap_base_seed": 42}`, but `UncertaintyConfig` in `config/model.py` requires `bootstrap_quantiles: list[float]`. The fixture is missing this required field. Currently no test uses `full_config`, so this has not surfaced as a failure. When a test eventually uses it, Pydantic will raise `ValidationError`.

- Recommendation: Add `"bootstrap_quantiles": [0.05, 0.50, 0.95]` to the `uncertainty` dict in the `full_config` fixture. Also add `"is_comparative_analysis": False`, `"alpha": 0.0`, `"beta": 0.0`, and `"weather_event_indices": ["event_type", "year", "event_id"]` to the `analysis_dict`, which are required for a non-comparative `SsfhaConfig`. Finally, add `"event_statistic_variables"` since `is_comparative_analysis=False` requires it.

**Test anti-patterns**

- `tests/test_old_code_alignment/conftest.py`: Module-level `sys.modules` mutation (described in Section 2.4). This is a test isolation hazard.

- `tests/test_event_stats_workflow.py::test_runner_cli_end_to_end`: This test constructs a `system.yaml` inline (lines 200-206) and writes it to `tmp_path`, then invokes the runner via `subprocess.run`. The test does not verify that the system YAML is valid against `SystemConfig` -- if the synthetic data schema changes, the hand-constructed YAML may silently diverge. Use `SystemConfig.model_validate(system_dict)` before writing to catch schema drift.

- `tests/test_event_stats_workflow.py::test_missing_timeseries_rejected`: This 40-line test (lines 119-185) constructs an entire test case inline rather than using the `test_case_builder` infrastructure. It duplicates synthetic data construction logic, making it fragile to schema changes. Refactor to use a builder function with the timeseries field omitted.

**Recommendations for old-code alignment Phases 3-8**

- Phase 3 (bootstrapping): The `assemble_bootstrap_sample` function has a subtle semantic distinction from the old code: it skips event-free years silently (correct behavior, documented), while the old code may have handled them differently. The alignment test should explicitly include resampled years that are event-free and verify the output event count matches expectations. Test with a fixed seed so the exact resampled years are known.

- Phase 4 (event statistics): The unseeded RNG issue (Section 1.2) must be fixed before alignment tests can be written, because the old code also uses `np.random.choice` without seeding. The alignment test will need to either: (a) seed both old and new functions identically and compare outputs, or (b) compare statistical properties (CI widths, quantile distributions) over many samples rather than exact outputs. Option (a) is strongly preferred.

- Phases 6-7 (orchestration notebooks, prospective DoD): The notebook fallback approach for 03A/03B/03C alignment is reasonable given that those modules are orchestration wrappers with no named functions. However, the notebooks should include checksummed input data and exact output values, not just "looks similar" visual comparisons. Pin the exact zarr stores used as inputs (e.g., store a SHA-256 hash of the input in the notebook metadata).

- Phase 8 (skill strengthening): The alignment protocol has proven its value -- the function inventory table in `master.md` is an excellent artifact. The `refactor-plan` skill update should mandate that every work chunk plan includes a pre-filled inventory table mapping old functions to new ones, rather than discovering gaps retroactively.

### Section 5: Maintainability for a Solo Researcher

**1. Pin your zarr encoding decisions now, before scale-up**

`io/zarr_io.py::default_zarr_encoding` uses Blosc/zstd at level 5 for all numeric variables. This is a good default, but the function does not pin the dtype. xarray will write whatever dtype the DataArray has at write time -- which may be float32, float64, or even object depending on upstream operations. During the Norfolk case study validation (Phase 06), a dtype mismatch between old-code outputs (likely float64 from raw NumPy) and new-code outputs (potentially float32 from Dask operations) will produce numerical differences that are compression artifacts, not algorithm errors.

Why this matters for a multi-year project: you will revisit these zarr stores months later, possibly on a different machine with a different Dask configuration. If the dtype is not pinned at write time, you cannot distinguish "the algorithm changed" from "Dask chose a different intermediate dtype."

Add explicit `dtype` entries to the encoding dict for all data variables. For flood depths and return periods, `float64` is the safe choice. For boolean masks, `bool` or `uint8`. Document the dtype policy in `default_zarr_encoding`'s docstring.

**2. Add a config hash to every output zarr's attributes**

Reproducibility in scientific computing requires knowing exactly which inputs produced which outputs. The current pipeline logs config parameters to stdout (which Snakemake captures), but there is no machine-readable link between an output zarr and the config that produced it.

Add a `config_sha256` attribute to every output zarr's root-level attrs. Compute it as `hashlib.sha256(json.dumps(config.model_dump(), sort_keys=True, default=str).encode()).hexdigest()`. This costs one line of code per write call and permanently links every output to its config. When you return to an output six months later, you can verify whether it was produced by the current config or a stale one.

**3. The "computation in core, I/O in analysis, CLI in runners" layering is well-designed -- protect it**

The separation of `core/` (pure computation, no I/O) from `analysis/` (orchestration with I/O) from `runners/` (CLI entry points) is sound and already consistent across implemented modules. This layering makes unit testing straightforward (test `core/` without touching disk) and keeps Snakemake integration clean (runners are thin CLI wrappers).

The risk is erosion. Phase 3D (PPCCT) and 3F (flood risk) will add new analysis modules. Each will be tempted to put "just a little" computation inside the analysis module for convenience (e.g., interpolation, grid alignment). Resist this. Every function that takes arrays and returns arrays belongs in `core/`. Every function that opens files or writes outputs belongs in `analysis/`. The boundary is: does this function need a file path? If no, it goes in `core/`. If yes, it goes in `analysis/`.

**4. The alignment testing protocol is your most valuable SE investment -- finish it before Phase 3D**

The function inventory table in the alignment testing master plan is the single most useful artifact in the entire planning corpus. It maps every old function to its new location, identifies gaps, and provides clear test targets. Phases 3-6 of the alignment protocol are pending, and 03D is blocked on them.

Do not treat the alignment backlog as something to "get to eventually." Every chunk implemented without alignment coverage is a chunk where subtle numerical drift can hide. The cost of finding a drift bug after Phase 06 (when you are comparing full Norfolk outputs and they do not match) is orders of magnitude higher than finding it now in an isolated unit test. Prioritize completing Phases 3-5 of the alignment protocol before starting any new feature work.

**5. Keep your test suite fast by default**

The current test suite is small enough that speed is not yet a concern. But integration tests (subprocess runner invocations, zarr round-trips) will accumulate through Phases 3D-06. A slow test suite creates pressure to skip tests during development, which defeats the purpose of having them.

Adopt a two-tier convention now: `pytest tests/` runs fast tests only (under 30 seconds total); `pytest tests/ --runslow` includes integration and HPC tests. Use `@pytest.mark.slow` for any test that takes more than 2 seconds or writes to disk. The existing `skip_if_no_slurm` and `skip_if_no_hydroshare` marks are a good start -- extend the pattern to a general `slow` mark. Configure `pytest.ini` (or `pyproject.toml [tool.pytest]`) to deselect `slow` by default.

### Mid-Refactor Review Lenses

The following lenses were developed specifically for mid-refactor scientific library audits. Apply them as you read the source code and plans. They should inform your findings across all sections.

1. **Semantic drift between old and new code paths** — A function's name and signature may survive the refactor while its behavior shifts subtly (changed defaults, different NaN handling, reordered axis). In scientific code this produces results that look plausible but are wrong. Diff actual numerical semantics against legacy equivalents, not just whether tests pass.

2. **Unit boundaries that will force a second refactor** — Early architectural choices (where Pydantic ends and xarray begins, what goes in zarr vs. what is recomputed, what constitutes a Snakemake "step") become load-bearing walls. For each module boundary ask: when phases 4–8 land, will this interface still work, or will it need to be torn open?

3. **Config/data coupling that undermines reproducibility** — The config schema often reflects "what the first few modules needed" rather than a principled decomposition. Look for runtime data (array shapes, CRS strings, paths discovered at execution time) that has leaked into config, or config values silently overridden downstream. Either pattern makes runs non-reproducible even when the config file is saved.

4. **Incomplete error-domain coverage in validation** — Solo researchers writing Pydantic validators typically cover cases they have personally encountered. Look for physically or statistically impossible inputs that are not rejected: negative discharge, probabilities outside [0,1], coordinate arrays that are not monotonic.

5. **Coordinate and dimension convention inconsistency** — When converting scripts to xarray, the most common subtle bug is inconsistent dimension naming or ordering across modules. Verify that a single documented dimension/coordinate convention exists and is enforced everywhere data crosses a module boundary.

6. **Test-oracle provenance** — Where did each test's expected values come from? If the oracle is "I ran the old script and saved the output," verify that the old script was run with the exact version, inputs, and parameters the test claims. A stale or misattributed oracle provides false confidence.

7. **Zarr/IO round-trip fidelity** — Every write-then-read cycle is a chance for dtype, fill-value, compression-induced precision loss, or coordinate encoding to silently change. The zarr schema is still evolving mid-refactor, so an early choice (float32 instead of float64, fill_value=0.0 instead of NaN) will propagate into every downstream store.

8. **Snakemake rule granularity vs. computational cost** — Rules too coarse lose restartability; rules too fine create filesystem/scheduler overhead. Assess whether the current rule design matches actual failure/restart boundaries. Bad granularity is painful to fix because all downstream input declarations need rewriting.

9. **Implicit state shared through module-level mutables** — Converting interactive scripts often promotes notebook-local variables to module-level constants or mutable defaults. Look for any module-level mutable state that could cause cross-test contamination or order-dependent behavior under parallel Snakemake execution.

10. **Execution-order assumptions that are no longer guaranteed** — Interactive scripts run top-to-bottom; a Snakemake-orchestrated library does not. Identify any place where module A's correctness depends on module B having already run and deposited a side effect (written file, cached value, modified global).

11. **Numeric-precision mismatches at the old/new boundary** — xarray may silently promote dtypes, reorder operations, or apply alignment relative to raw NumPy. Alignment tests should use tolerances *justified by the computation's actual precision requirements*, not set loose enough to make the test pass. An unjustified tolerance hides real bugs.

12. **Documentation that describes the plan, not the code** — Mid-refactor, docstrings tend to describe intended behavior rather than current behavior. Flag any docstring or planning doc that asserts something the code does not yet do (or does differently). Each mismatch should be fixed or explicitly marked aspirational with a tracking reference.

### Tone and Style

- Begin each finding with the finding statement. Do not open with "It's worth noting that," "This is a common pattern in," or similar preamble. Lead with the verdict.
- Reference actual file paths and function names from the code you read.
- Do not praise decisions for the sake of balance. If something is well-done, one sentence is sufficient.
- The user is a capable scientist actively learning SE — assume strong domain knowledge, growing SE fluency.
- Depth over breadth: a few well-developed findings per section beat a long list of shallow observations.
